## 1. 执行顺序与依赖

强制顺序：**B2 收尾 → B4 → B5 → B6 → B7 → B8 → B9 → B10**。

依赖理由：B4 的调用账本是 B5 渠道预算的计数基础；B5 的预留语义决定 B7 候选扩展时哪些资源已被占用；B7 的有界候选集合是 B8 提交边界的前置；B8 定义的"首次有意义内容"边界是 B9 判断续接可否迁移的依据；B10 只做暴露与验收，不引入新语义。

B2 收尾（投影版本）优先于一切，因为它影响迁移正确性——投影语义已变而版本号未动，旧快照行会被误当同版本读取。

## 2. 各批次目标与完成判据

### B2 收尾：投影版本
升 `ChannelCapabilityProjectionV2`，并让索引重建拒绝旧版本行。
判据：旧投影行不进入候选；升级后首次刷新重建全部渠道；跨版本读取有明确拒绝原因而非静默跳过。

### B4：请求与单次尝试生命周期分离
把 `releaseRouteAttemptLease` 与 `finalizeRequestExecution` 收敛为单一释放路径，统一错误、取消、重试与释放；用户名额覆盖整个请求，渠道名额覆盖单次尝试，换渠只释放旧渠道资源。
判据：无重复预扣、无租约泄漏；客户端取消与租约失败不惩罚供应商；健康归因独立于重试资格。

### B5：渠道 RPM／TPM 预算
渠道侧新增 RPM 与 TPM 预算，与用户侧共用 Redis 原子固定窗口和服务器时间。TPM 预留输入估算与有效输出上限，完成后按 usage 校正；无法确定安全上界时该请求不进入启用 TPM 的候选。渠道 RPM 每次实际发送计一次，容量拒绝不消耗上游发送预算。已启用的硬限制不在 Redis 故障时降级为节点计数。
判据：多实例限制一致；超时、取消、重试计数与 Redis 故障均通过。

### B6：`RequestRequirements` 单一来源
每个请求只生成一份要求（协议、流模式、输入模态、工具类型、结构化输出、推理、续接状态），供候选过滤、预览和转换共用。先原生／语义完整路径，耗尽后进入参考实现支持的兼容候选；兼容候选仍受权限、活动组、倍率、健康和容量约束。已知损失形成结构化诊断，不插入模型正文；硬错误（不可重建续接、非法请求、权限失败、无转换器）不得兜底。
判据：四协议矩阵与关键语义边界通过；预览与实际选渠给出一致的候选资格判断。

### B7：负载与健康调度
实际负载快照、EWMA（系数 0.2，按渠道／实际模型／协议／流模式隔离，超五分钟未更新视为未知）、层内可复现加权无放回选择、有界候选扩展（自动初选 TopK 7、准入探测最多 64、实际发送仍最多 3）。Priority 保持硬分层；负载快照只用于排序，Redis 租约负责最终准入。
判据：首选满载后能找到后续资源；探测与发送预算分别受限且互不透支。

### B8：流式提交与超时
提交前最多缓冲 1024 条非内容事件或 8 MiB，超限明确失败并停止重试；首次有意义内容作为提交边界；提交前不发送会提前提交 HTTP 的 ping；分别记录连接、首事件、首内容、空闲及总期限。
判据：metadata 后失败、首内容超时、提交后断流、缓冲超限、慢客户端与取消均不泄漏失败尝试、不拼接响应。

### B9：亲和与续接
Sticky 是有资格候选内的偏好，手动顺序在当前兼容候选集合内生效且不跨活动组；供应商续接状态绑定用户／Token、渠道及凭据身份，只有完整上下文可重建时才允许迁移。
判据：不串用户、不丢状态、不随机迁移不可重建的续接。

### B10：诊断、接口与总验收
暴露调用／尝试详情、降级提示、限额与监控界面，接上目前无调用方的 `RouteLeaseMetrics`、`RouteDecisionEventsDropped`、`RouteCapabilityRefreshLagSeconds`；同步文档、OpenAPI、前端与模拟器；执行迁移矩阵与停机验收。
判据：计划第 5 节"必须通过的检查"全部有结论（通过或明确未通过），迁移对账与恢复证据齐备。

## 3. 每批次的固定动作

1. 读相关源码与既有测试，确认差量与影响面。
2. 实施，保持 Router → Controller → Service → Model 分层与 RelayKit 独立性。
3. 验证顺序：定向测试 → 类型／lint → 构建 → 烟测；后端单测 60 秒超时；主模块、RelayKit 分别验证。
4. 提交，信息含实现、已跑验证、**未完成项**。
5. 更新 `docs/implementation/ROUTING_RETIREMENT_PROGRESS.md`。

## 4. 验证口径

- 不把静态阅读、未执行命令、模拟器 fixture 或缓存结果报告为通过。
- 复用未变化代码已通过的结果；仅在相关改动、失败或未解疑问后重跑。
- 文档级改动不触发应用构建与运行时套件。
- 真实数据库矩阵、Playwright 与停机验收统一在 B10 执行，中途不声称已完成。

## 5. 交叉审计（最终步骤）

全部批次完成后，将改动交由 GPT 与 Claude 交叉审计，各自独立出具结论后由我汇总分歧。

审计范围：计费与配额不变量、准入与租约正确性、数据迁移可逆性与阻断条件、协议转换语义与硬错误边界、流式提交与终止、并发与多实例一致性、旧字段是否真正清退、测试是否保护真实契约。

审计输入：完整提交序列 diff、进度记录、本计划、已执行验证结果清单（含未通过项）。审计发现按"确认缺陷／可能问题／建议"分级；确认缺陷在交付前修复并复验。
