# 恢复与人工对账

钱包与有限 Token 的预留执行 `available -= R; reserved += R`。结算实际费用 C 执行 `available += R-C; reserved -= R; used += C`；超预估允许产生欠费，下一次付费请求停止准入。无限 Token 不限制可用预算，但记录 reserved 和 used。确认未发送或明确拒绝可释放；未知是否接受、缺用量、断流或进程退出本身不能证明免费。

恢复任务读取主数据库的持久化状态。已有结算/释放意图重放相同金额和事件；资金事务成功但日志失败时仅重试投递。异步任务提交成功保持预留，收到终态才结算或释放；已知任务终态但费用无法计算，保存任务终态和待对账证据，停止重放上游。Realtime 保存累计用量和报价，累计补预留失败时停止继续生成，最终按累计费用统一舍入。

Root 在控制台“账务对账”处理：

1. 打开记录，核对请求 ID、钱包、Token、冻结报价、各次尝试与时间、规范用量、费用分项及历史事件。
2. 若金额已确认，只是事务或日志投递失败，点击重试。重试不重新请求上游，也不读取新价格。
3. 若接受状态或金额未知，先依据已保存证据及人工取得的供应商记录判断。确认消费后填写最终 quota；只有确认无需收费时选择释放。填写具体理由。
4. 保留操作 ID 处理网络重试。409 表示版本或内容冲突，重新加载，核对别人或恢复任务已做的决定；不要自动更换 ID 重复扣款。
5. 核对资金事件、钱包与 Token 的预留清零、任务费用、日志及统计金额一致。日志仍不可用时保留待投递状态，继续重试投递。

已结束记录不可用新操作重写。人工结算与自动恢复在同一请求锁上串行，只有一方产生最终资金事件；人工金额继续驱动同一消费结果，保留已知任务关联和渠道归属。

SQL 日志使用事件 ID 唯一键。ClickHouse 先保存写入意图，结果不明时按事件 ID 查询确认；查不到且已有写入意图时保持待对账，不盲目重写。关闭展示日志不会删除资金流水。缓存、日志与统计不能作为余额来源。

指标查询失败明确显示不可用。`idempotency_conflicts` 是当前进程累计计数；`debt_events` 来自不可变流水。预留总额来自钱包，不能把 Token 预留再加一次。等待时间包括仍在途和待处理请求，应结合状态判断。当前实现保留单实例契约；SQLite 单写连接与有界锁冲突重试，MySQL/PostgreSQL 使用统一行锁助手。

新版本只允许空库安装或带本版本账务标记的重复启动。发现已有旧数据库立即报错，既不迁移也不清空。上线需另行批准并遵循既有部署流程；不要将现有生产数据库直接配置给候选版本。故障排查可读取本次事件与状态，不得通过直接 UPDATE 余额修账。
