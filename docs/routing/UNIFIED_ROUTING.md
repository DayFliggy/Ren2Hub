# 渠道路由

核心以平台渠道为最小单位。一条渠道一把 Key，提供商插件渠道一份凭据，所以选中渠道就选定了发出请求的凭据，渠道状态、熔断和冷却都不区分 Key。业务分组及组间价格、跨组重试均退役；旧组库在迁移之前拒绝启动。NewAPI 是唯一上游，协议、认证、错误重试和任务生命周期仍以其原生实现为基础。

每个 Key 可在全平台自动选路，也可在所选渠道内自动或顺序选路。没有配置时使用全平台。指定列表后只使用启用的条目，全部停用或被管理员删光时返回 503 `model_not_found`。顺序模式按条目顺序检查容量，自动模式在候选集合内使用健康、质量、权重、负载和会话亲和。两种方式都检查渠道状态、模型、端点和 Key 倍率上限。缓存和数据库只提供事实，由同一资格服务和选择器决策。与上游 `GetChannel` 一样，声明了请求精确模型名的渠道优先；只有这些渠道在全部规则（含 Key 倍率上限和所选渠道列表）之后一个都不剩，才改用归一化模型名（例如去掉 `@` 修饰）匹配。预览同样按这条规则，只声明归一化名的渠道在有精确渠道可用时标为 `exact_model_preferred`。

自动路由先按健康准入选择，再比较动态质量档、管理员默认优先级、正权重、负载档和请求内加权随机顺序。同档同默认优先级且都有限额时，以在途数占上限的四分位分档；都无限额时使用绝对在途桶，混合组直接进入末级。相同负载档的价格系数为 `max(0.85, sqrt(组内最低倍率 / 渠道倍率))`。等权两家相差两倍价时，便宜渠道约占 54%。

每轮普通自动扫描在管理员日志的 `admin_info.request_policy` 中记录 `scan` 事件。按请求从 1 编号，`candidates` 为静态筛选后的候选数，`full_skips` 只统计实际拿槽时遇满的次数，`duration_us` 从候选查询计至准入结束，以微秒计。结果见 `decision.reason`（`selected`、`full`、`no_candidate`、`error`）。`ranked` 按实际访问顺序列出最多 8 次访问，每项含 `channel_id`、`health`、`band`、已知时的 `cache_band`、`priority`、`weight`、`load`、`price_factor`、探索标记 `explore`，以及被跳过时的 `skip`（`full`、`cooling`、`open`、`probe_busy`、`deleted`）；技术错误中止扫描时，导致中止的那个候选作为最后一项记入，`skip` 为 `limit_unavailable`（读不到并发上限）或 `error`，返回的 HTTP 错误不变；冷却渠道在兜底轮被再次访问时会出现两次。每项约 100 字节，最长约 170 字节，一条 `scan` 最多增加约 1.4 KB。普通用户的日志不含 `request_policy`，也就看不到 `ranked`。任务消费日志也通过管理员的 `request_policy` 字段提供扫描摘要。亲和直达、固定和顺序路由均不产生自动扫描摘要。共享插件端点预选后，正式复用渠道时才记入选中事件。原始模型名未匹配而转入插件解码时，按最终选路记录；实际满载或存储故障会记录失败。

首轮拒绝或重试结束时可能没有对应的数据库日志行。按请求 ID 搜索服务端 `route_scan`，可查当轮满载、无候选、存储错误，或在发送前被本地拒绝的选中结果。后一种记录含 `channel_id` 和 `request_status`，例如预扣被拒时为 403。Token 路由配置读取失败发生在候选查询之前，此时查询 `route_scope stage=token_route_scope result=error`。

上游结构化错误码 `insufficient_quota`、`insufficient_user_quota`、`pre_consume_token_quota_failed` 在任意 HTTP 状态下都属于额度信号。观测到上游真实返回 HTTP 402 时同样直接识别；渠道状态码映射后的根错误 402 不作为额度信号。非 429 响应还识别余额不足文案：错误类型须为通用的 `invalid_request_error` 或 `upstream_error`，OpenAI 兼容格式须没有独立错误码；剔除引号内的回显并去除首尾空白后，消息以 `Your credit balance is too low` 开头，或中文消息的第一个分句包含“余额不足”“额度不足”“额度已用尽”“账户已欠费”“积分不足”。中文判断还剔除单引号、‘…’、「…」和『…』包住的回显，只检查第一个“：:，,。；;!！?？”之前的文本；英文分支保留原有撇号规则。明确的其他错误码和其他错误类型不按文案识别。根错误或观测状态任一为 429 时，文案不能触发额度分类，只有结构化额度码或观测到的真实上游 402 可以。Gemini 每分钟限流的 `RESOURCE_EXHAUSTED` 即使带额度文案，也按普通 429 处理，生效冷却期间不计熔断。

额度信号计入模型熔断和动态质量，尝试证据记录 `outcome_reason=upstream_quota`。额度 429 同时设置渠道冷却。本地用户余额、令牌额度、钱包预扣拒绝，以及已取消、超时或标记为业务拒绝的请求均不触发额度分类。流式请求已经输出首个内容事件后，不再用额度信号改写最终分类，熔断按首输出结算成功。

充值后，已打开的熔断在本轮约 1 分钟的暂停期结束时进入半开，连续 3 次真实探测成功后恢复。质量每 5 分钟评估一次。成功率降档至少经过 15 分钟才可恢复，降档后的新样本和参考样本各须达到 50，成功率差小于 2 个百分点且重新评估回到正常档。旧失败样本在约一小时内退出窗口，质量排序可能滞后约一小时。若新流量或参考样本不足，降档可持续更久。

自动停用和定时测试成功后的启用都会发布渠道配置，并清除这条渠道各模型的熔断与动态质量记录。一个模型的测试成功后，同渠道持续故障的其他模型也从空记录重新积累失败。

同一渠道与模型的请求间隔超过 5 分钟时，闭合熔断的连续失败计数可能在下次尝试前清零。每小时不足 50 个有效样本时，成功率也不能触发动态质量降档，持续故障的低流量模型可能长时间参与正常排序。

熔断按渠道与映射后的实际模型计数。连续 5 次失败或 60 秒内至少 20 次有效尝试且失败率达到 50%时暂停一分钟。上游把上下文超长包成没有可识别错误码的失败（例如中转商的 500）时，只要错误来源是上游、状态码不是 401、402、403、429，根错误的错误码和类型不属于原生分类列出的凭据、额度、限流、权限一组（与快照错误码共用同一张表），且上游错误消息命中上下文超长短语（表在 `service/route_outcome.go`），这次尝试对熔断、动态质量和观测样本计为 ignored，逐次尝试证据带 `outcome_reason=request_context_overflow`；重试、原生性能统计和客户响应不变。错误消息取归一化后的上游错误文本：错误对象的 message；没有错误对象时是原生处理器从 `detail` 等顶层字段取出的消息；OpenRouter 的 metadata 已拼在其中。不扫完整响应体；双引号、弯引号（“”）和反引号内的回显先剔除再匹配，单引号不剔除（它同时是撇号）。规范的限额报告句式（maximum context length is 加数字，如 “This model's maximum context length is 128000 tokens”）单独即算超长；只点名上限的其他短语（如单独的 maximum `ObserveRouteUsage`，原始帧里出现正常完成标记（chat 的 `finish_reason` 为 stop、tool_calls 或 function_call，Claude 的 end_turn、tool_use 或 `message_stop`，Gemini 的 `finishReason: STOP`，Responses 的 `response.completed` 或状态为 completed 的 `response.done`），且原始帧没有任何载荷；其余记 ignored（`no_visible_output`），因为误判失败会让健康渠道熔断。原始帧的载荷按同一张内容表识别，例如 chat 尾帧里的有名工具调用、Gemini 的 fileData；原生没把它转发给客户（chat 客户端没要求 usage 只含空文本片段（`output_text`/`text` 且 `type` 以外的字段都为空）的 message 项，证明为空；空文本但带非空注释（如 file_citation）的片段算载荷，因为注释会发给客户；列出其他项（例如只有加密推理或未知类型）也算载荷，直传和转 chat 都不判空流。内容按各协议 DTO 已定义的输出载荷识别，包括 chat 的音频与 refusal、Gemini false`（客户端直接给出，或渠道参数覆盖、出站插件注入；客户端显式给出的值优先于覆盖）时只写入输入、不要求生成（客户端用它预热连接），这类请求原生成功且没有输出时记 ignored（`no_generation`）：不算空流，也不算生成成功，不推进半开恢复、不清零连续失败、不写质量、观测和缓存样本，探测许可照常在结束时释放；它的上游失败仍按原生分类计；HTTP Responses 与 chat `empty_stream`：路由尝试只能读到参数覆盖之前的客户请求，读不到实际发给上游的停止串，这是已知限制；处理器从未报告事件的流保持原生结果；客户响应、计费、重试和原生性能统计不变，非流式空响应不在此列。半开只允许一个真实探测，连续成功 3 次恢复。流式探测在首个内容事件到达时就按成功结算并让出探测许可，下一个请求可以接着探测；派发时不是流式、上游返回 SSE 后才转入流式处理的请求同样如此，转成缓冲响应的分支不报告首输出，仍在结束时结算。渠道并发槽仍到这次尝试结束才释放，结束时不再重复计入熔断；结束遇到正在写的首输出结算时等它写完再释放许可。首个内容事件之前失败的流式探测和非流式探测照旧在结束时结算。429 按渠道冷却，缺少 Retry-After 时为 5 秒，最长 5 分钟。一次尝试遇到普通限流 429 既不写冷却，也不计入当前熔断。全部熔断暂停时返回 503，可用渠道全满时返回 429；仅当没有正常渠道且存在只因 429 冷却的渠道时才从冷却渠道派发。插件预选只读，正式重取时重新核对状态。配置发布会隔离旧代际的结果。Root 专用的 `/api/performance/routing` 快照里，打开和半开的熔断带 `trigger`（`consecutive`、`window_rate`、`probe_failed`）、最近一次失败的 `last_status` 和 `last_error_code`（只保留 `service/route_error_codes.go` 错误码表里的码：原生分类器点名的上游码、本网关生成的 relaykit 错误码和路由原因；其余一律记为 `unrecognized`，不含上游消息；客户收到的原始错误不变）、本次打开的 `opened_at` 和探测失败重开次数 `reopens`；闭合或配置发布后这些信息随熔断状态一起清除。冷却带 `source`（`retry_after` 或 `headerless`），只延长不缩短，来源随生效的那次冷却。

动态质量在进程内保留一小时的样本，每五分钟评估一次。对同一请求模型、操作和流式类型比较成功率、延迟、输出速度、缓存复用率，取证据充分的最差档。成功率至少 50 个样本，延迟和速度各至少 20 个有效样本；流式速度只计完整成功且真实输出至少 50 token、生成至少 0.5 秒的尝试。配置失效和重启后从默认优先级起步。管理员日志按本轮尝试记录耗时、首输出、用量来源、质量与选路原因。

缓存以真实读取 token 除以完整输入 token。仅在有身份和有效期证据的复访中使用缓存档，分显式、自动模式，按两家共同的长度、冷热和来源分层比较。每侧至少 50 次有效尝试、10 个会话、80% 字段覆盖；有效差异达 20 或 40 个百分点且连续两轮有新会话证据才降档。未报字段与显式零区分，超长输入或单会话主导时保持未知。未知渠道保留前三项与末级规则产生的位置。自由首轮流量的探索软预算为 5%，按会话复访延续；满额暂停接纳新探索会话。带已有上游资源引用时沿用原路由边界。

亲和键由规则名、模型和请求值组成，不含令牌。候选集合不同的两个令牌共用同一会话值时，可能互相清除亲和绑定，strict 模式下返回 503。

prefer 模式的会话亲和在亲和渠道合格时直接使用；渠道被禁用、健康暂停、满载或不在当前候选中时退回正常选路，不报错。亲和渠道在本请求的模型、操作和流式类型上处于质量 2 档（成功率、延迟或速度严重降档；缓存档不算）时，本次按本请求的自动排序（含本请求的缓存档）依次以正常准入尝试质量档更好的候选，遇熔断、冷却或满载跳过，占到槽就改走该渠道，选路来源记为 `affinity_exit`，绑定不清除；成功后开启 `switch_on_success` 时改绑到实际服务的渠道，关闭时绑定保持原渠道、不改写也不续期；没有更好的候选能准入时仍用亲和渠道。这一步不运行探索，不占探索预算。插件共享端点重取遇到这种退出时返回重选。strict 不受影响；默认的 Codex CLI、Claude CLI 规则没有设置 `session_mode` 且带 `skip_retry_on_failure`，按 strict 处理，同样不受影响。strict 模式只用绑定渠道，熔断打开视为绑定渠道不可用，与上游对不可用亲和渠道的处理相同：返回 503 `strict_session_binding_unavailable`（带 Retry-After），除非开启 `keep_on_channel_disabled` 否则清除绑定，同一会话的下一个请求按正常选路并写回新绑定。清除前重读绑定，只有它仍指向本次判定不可用的渠道才删除，所以重读之前已改绑的情况会保留。读与删是两次缓存操作，不是原子的：重读之后、删除之前写入的新绑定仍会被删；较早派发的成功请求回写也会覆盖较新的绑定（上游行为，见[等待上游](../upstream/WAITING_UPSTREAM.md)）。prefer 模式因 Token 路由禁止清除绑定时用同一条件。strict 遇到半开且没有在途探测时本请求作为探测发送，探测占用时同样 503 并清除绑定；只因 429 冷却时照常发送并保留绑定；满载 429 和读取上限失败 503 都保留绑定。插件共享端点的正式重取与亲和选路共用同一条准入规则。固定、手动列表、原任务续作和已锁定的 WebSocket 不受影响。普通非 AdvancedCustom 渠道按 b388 原生规则不在选路阶段预筛 `/v1/responses/compact` 能力；高优先级不支持渠道可能在运行时返回不可重试 400，不能承诺转用次优渠道。AdvancedCustom 的路径校验、提供商插件身份和原生计数扩展的资格校验继续保留。非锁定重试分支在已收到供应商错误后遇到任何选路失败（无候选、全部满载、选路存储故障），HTTP、Responses WebSocket 和任务均保留上一次实际发送后返回的错误；任务通过传输层发送标记判断，包括响应解析产生的本地 502，原样保留 TaskError 的状态、数据及标志，实际选路错误仍记录日志。首轮没有供应商错误时返回当轮选路错误。任务显式取消优先返回 request_cancelled；原渠道锁定分支仍返回当次重新准入的倍率、权限、满载或存储错误。预扣和请求体失败不属于选路错误保留范围。任务在选路成功后、提交之前再次检查取消，已取消则不发送，返回 408 并由原生命周期退款及释放许可。

用户及渠道并发默认 0 表示无限，仍统计在途数，不排队。删除渠道或硬删除用户后，空闲的并发表项移除，仍有在途许可的表项在最后一个许可释放后移除。之后同 ID 的准入先读数据库：记录不存在就拒绝（选路跳过该渠道，prefer 亲和退回正常选路；用户请求返回 403 `user_unavailable`）。删除或改上限先提交数据库、再发布待刷新标记；标记生效后，删除前取得旧数据的请求不能重建表项，提交到发布之间已读到旧数据的请求仍按旧上限准入，这个窗口的上界未测量；同 ID 的记录重新存在时，新渠道或用户沿用在途计数并按数据库中的上限准入。用户槽覆盖逻辑请求及其重试；渠道槽覆盖一次真实尝试及资源清理。热更新保留活动计数，Release 幂等。用户满立即 429 `user_concurrency_exceeded`；渠道满扫描下一候选，全部合格渠道满时 429，无合格渠道则路由不可用。读取上限失败返回 503 `<kind>_concurrency_unavailable`，不再试下一个候选；strict 会话亲和遇到它同样返回 503 并保留绑定。普通 HTTP/WS 准入使用 `service.ConcurrencyAdmissionError` 映射。MJ image-seed 仍沿用上游封装：除满载外的准入错误返回 400 `code=4`，包括读取上限失败；不能将它声称为统一 503。

发送顺序为认证解析、用户占槽、选渠道、渠道占槽、资格与倍率复核、原生估算预扣、发送、观察与结算释放。每个逻辑调用只有一个 BillingSession；不使用信任免预扣，更贵重试须先有余额补足。模型基础价乘绑定渠道倍率一次，在原生最终取整前应用。任务在提交时保存渠道倍率和其他倍率（时长、尺寸等），后续改渠道倍率不影响在途任务。完成时按 token 重算的任务与上游一样读完成时的模型倍率配置：是否重算、模型倍率取多少都看那时的配置，管理员调价会影响在途任务的最终金额，调高多收、调低少收。见[资金实现](../billing/IMPLEMENTATION.md)。

Responses WS 按每次 create 重新认证、资格检查及占槽，空闲连接不占；已建立的会话固定在原渠道。若该渠道退出启用的选择范围，包括全部条目停用或被删光，后续 `response.create` 返回 403 `access_denied` 错误事件。重连时重新选渠，空选择范围返回 503 `model_not_found`。Realtime 占整次连续会话。异步任务只在提交或实际轮询 HTTP 时占渠道槽，不在后台等待期间持槽。轮询时渠道满载或读取上限失败只跳过本轮，不计上游失败；准入时发现渠道已删除同样只跳过本轮；原生批量轮询读不到渠道时把任务判为失败且不退款，与上游相同，见[原生回归的行为变化](../upstream/NATIVE_B388_DISCLOSURES.md)。普通 HTTP 成功路径中，客户端断开不自动取消已发送的供应商请求；渠道槽位保持到供应商尝试结束，之后结算一次、释放一次。这个合同不承诺对失败响应禁止重试，也不承诺立即退款。

已接受任务的续作固定原渠道，不因 Key 偏好变化重放到其他渠道。插件原任务引用和 Midjourney 续作（change、simple-change、modal、video、action、image-seed）的原渠道准入由 `service.AcquireOriginTaskRouteChannel` 判定：只豁免所选渠道列表，仍比较 Key 的最高渠道倍率。超限在渠道占槽、预扣、发送之前拒绝，不换渠道；没有上限或恰好等于上限允许。普通任务返回 400 `channel_ratio_exceeded`，MJ handler 保留自身封装；经 Distribute 提前拒绝的 MJ 提交仍使用 OpenAI 错误体。请求级路径、WS 和插件身份过滤器，渠道存在/启用、倍率合法及即时容量照常检查。找到 MJ 原任务后只准入一次，使用原渠道的 Key。

原渠道删除或禁用返回 400 `origin_task_channel_disabled`，满载 429，原渠道准入或 ApplyChannelPin 的存储故障 500；插件准备阶段仍沿上游统一返回 400 `origin_task_channel_disabled` 且不暴露底层错误；image-seed 的封装例外见上文。Key 模型限制保留上游现状。原生 remix 在原渠道上下文未初始化时仍可能发生 NewAPI 共有的 nil pointer panic，阻断后续预扣和发送。这个问题以及原模型推导、原生平台核对、remix 动作、ID 和继承倍率都与上游相同，没有在本地修复，见[等待上游](../upstream/WAITING_UPSTREAM.md)；不能声称这些路径已可用。插件原任务平台校验仍使用准备阶段候选元数据，尚不等同于实际执行插件的归属校验。

不存在或不属于当前用户的原任务、管理员指定渠道、存储失败与模型限制的错误顺序沿用共有实现；不承诺所有入口均在选路之前返回同一种不存在错误。MJ image-seed 仍使用吞掉数据库错误的旧查询，共有错误分类待上游处理。完整范围、源码位置与诊断见[等待上游列表](../upstream/WAITING_UPSTREAM.md)。

共享插件端点沿用上游的类别锁定：首次选中普通渠道后，重试不跨到插件渠道，反向亦然，顺序列表顺延也受该规则约束。另有两项与上游相同的限制。先选路后解码，普通渠道胜出时不建立插件原任务 pin。选路不按 stream/sync/background 过滤插件候选，只支持 background 的插件渠道胜出时，stream/sync 请求返回 400。管理员可以把这类插件渠道的优先级调到可用普通渠道之下来规避；优先级相同时，健康、负载、延迟和权重排序仍可能选中插件渠道，普通渠道全部不可用时也会落到插件渠道。

主要接点为 `service/route_candidates.go`、`service/channel_select.go`、`service/concurrency.go`、`service/route_attempt.go`、`service/billing_session.go`。接口与版本冲突见[网关 API](GATEWAY_API.md)，不恢复 `/api/next` 或第二套路由管线。

预览的 `transport` 为 `http` 或 `websocket`，默认 `http`；`stream` 单独表示 HTTP 流式，WS 固定为流式且只支持 `/v1/responses`。预览与运行时共用路径资格、插件身份、宿主端点过滤器及模型规范化，使用同一插件注册表代际；响应回传实际解析的模型和传输方式。任务提交路径使用运行时的 VideoSubmit 观察桶排序。普通 HTTP 路径排除无关 TaskPlugin 渠道；共享宿主端点首次按原模型名允许合格的普通渠道及所有声明该端点的候选插件；原名无候选而回退到插件规范名后，追加与运行时一致的插件身份过滤，只保留该身份渠道。管理员给插件渠道声明非规范拼写时，阶段一命中后仍可能在执行时规范化并重新选路。`/v1/tasks/:key` 固定插件身份。其他依赖插件请求解码的路径返回 `400 preview_path_unsupported`。预览不运行 JS、不占槽、不预扣、不发送请求；共享端点依赖请求体的模式检查仍发生在执行时，静态资格不是提交成功保证。

多行渠道写和路由保存共用 `model.lockChannels`：完整 ID 集合去重、升序后再按 200 行分块；保存使用 SHARE，六个可达批量写入口使用 UPDATE。按 tag/status 取候选后锁定并按原数据库谓词复核，只修改实际锁住的行；渠道和能力行在同一事务内写入，通过事务读取更新值，提交后按实际 ID 发布缓存/并发/观察状态。锁序为 Token（ID 升序）→渠道（ID 升序）→路由配置/条目，渠道→能力；历史无调用的 DeleteChannelByStatus/DeleteDisabledChannel 未扩改，不属于六入口覆盖。
