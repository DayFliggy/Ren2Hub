# 渠道路由

核心以平台渠道为最小单位。业务分组及组间价格、跨组重试均退役；旧组库在迁移之前拒绝启动。NewAPI 是唯一上游，协议、认证、错误重试和任务生命周期仍以其原生实现为基础。

每个 Key 使用自动或手动模式。自动候选来自全平台，受渠道状态、模型与原生端点支持、Key 模型限制及最高渠道倍率约束。手动模式使用一份有序列表，只跳过禁用、不合格、超倍率及满载渠道；空列表返回无可用渠道，不回退自动。缓存和数据库只提供事实，由同一资格服务和选择器决策。与上游 `GetChannel` 一样，声明了请求精确模型名的渠道优先；只有这些渠道在全部规则（含 Key 倍率上限和手动列表）之后一个都不剩，才改用归一化模型名（例如去掉 `@` 修饰）匹配。预览同样按这条规则，只声明归一化名的渠道在有精确渠道可用时标为 `exact_model_preferred`。

自动路由先按健康准入选择，再比较动态质量档、管理员默认优先级、正权重、负载档和请求内加权随机顺序。同档同默认优先级且都有限额时，以在途数占上限的四分位分档；都无限额时使用绝对在途桶，混合组直接进入末级。相同负载档的价格系数为 `max(0.85, sqrt(组内最低倍率 / 渠道倍率))`。等权两家相差两倍价时，便宜渠道约占 54%。

每轮普通自动扫描在管理员日志的 `admin_info.request_policy` 中记录 `scan` 事件。按请求从 1 编号，`candidates` 为静态筛选后的候选数，`full_skips` 只统计实际拿槽时遇满的次数，`duration_us` 从候选查询计至准入结束，以微秒计。结果见 `decision.reason`（`selected`、`full`、`no_candidate`、`error`）。`ranked` 按实际访问顺序列出最多 8 次访问，每项含 `channel_id`、`health`、`band`、已知时的 `cache_band`、`priority`、`weight`、`load`、`price_factor`、探索标记 `explore`，以及被跳过时的 `skip`（`full`、`cooling`、`open`、`probe_busy`、`deleted`）；冷却渠道在兜底轮被再次访问时会出现两次。每项约 100 字节，最长约 170 字节，一条 `scan` 最多增加约 1.4 KB。普通用户的日志不含 `request_policy`，也就看不到 `ranked`。任务消费日志也通过管理员的 `request_policy` 字段提供扫描摘要。亲和直达、固定和手动路由均不产生自动扫描摘要。共享插件端点预选后，正式复用渠道时才记入选中事件。原始模型名未匹配而转入插件解码时，按最终选路记录；实际满载或存储故障会记录失败。

首轮拒绝或重试结束时可能没有对应的数据库日志行。按请求 ID 搜索服务端 `route_scan`，可查当轮满载、无候选、存储错误，或在发送前被本地拒绝的选中结果。后一种记录含 `channel_id` 和 `request_status`，例如预扣被拒时为 403。Token 路由配置读取失败发生在候选查询之前，此时查询 `route_scope stage=token_route_scope result=error`。

熔断按渠道与映射后的实际模型计数。连续 5 次失败或 60 秒内至少 20 次有效尝试且失败率达到 50%时暂停一分钟。上游把上下文超长包成没有可识别错误码的失败（例如中转商的 500）时，只要错误来源是上游、状态码不是 401、402、403、429，且上游错误对象的消息字段命中上下文超长短语（表在 `service/route_outcome.go`），这次尝试对熔断、动态质量和观测样本计为 ignored，逐次尝试证据带 `outcome_reason=request_context_overflow`；重试、原生性能统计和客户响应不变。只看消息字段，不扫响应体；流式错误事件不保存上游消息，这类不识别。流式请求以第一个有内容的事件为成功界；流正常结束、观察器收到过事件却没有任何内容事件时，上游用量报告输出 token 大于 0 记 ignored（`no_visible_output`），流以内容过滤、安全、拒绝或长度上限结束记 ignored（`request_terminated`），其余记失败（`empty_stream`）。结束原因读 chat 的 `finish_reason`、Claude 的 `stop_reason`、Gemini 的 `finishReason` 与 prompt 拦截、Responses 的 incomplete 原因，内容事件和结束原因的表都在 `service/route_stream_output.go`。处理器从未报告事件的流保持原生结果；客户响应、计费、重试和原生性能统计不变，非流式空响应不在此列。半开只允许一个真实探测，连续成功 3 次恢复。流式探测在首个内容事件到达时就按成功结算并让出探测许可，下一个请求可以接着探测；渠道并发槽仍到这次尝试结束才释放，结束时不再重复计入熔断。首个内容事件之前失败的流式探测和非流式探测照旧在结束时结算。429 按渠道冷却，缺少 Retry-After 时为 5 秒，最长 5 分钟。全部熔断暂停时返回 503，可用渠道全满时返回 429；仅当没有正常渠道且存在只因 429 冷却的渠道时才从冷却渠道派发。插件预选只读，正式重取时重新核对状态。配置发布会隔离旧代际的结果。Root 专用的 `/api/performance/routing` 快照里，打开和半开的熔断带 `trigger`（`consecutive`、`window_rate`、`probe_failed`）、最近一次失败的 `last_status` 和 `last_error_code`（错误码最长 64 字符，不含上游消息）、本次打开的 `opened_at` 和探测失败重开次数 `reopens`；闭合或配置发布后这些信息随熔断状态一起清除。冷却带 `source`（`retry_after` 或 `headerless`），只延长不缩短，来源随生效的那次冷却。

动态质量在进程内保留一小时的样本，每五分钟评估一次。对同一请求模型、操作和流式类型比较成功率、延迟、输出速度、缓存复用率，取证据充分的最差档。成功率至少 50 个样本，延迟和速度各至少 20 个有效样本；流式速度只计完整成功且真实输出至少 50 token、生成至少 0.5 秒的尝试。配置失效和重启后从默认优先级起步。管理员日志按本轮尝试记录耗时、首输出、用量来源、质量与选路原因。

缓存以真实读取 token 除以完整输入 token。仅在有身份和有效期证据的复访中使用缓存档，分显式、自动模式，按两家共同的长度、冷热和来源分层比较。每侧至少 50 次有效尝试、10 个会话、80% 字段覆盖；有效差异达 20 或 40 个百分点且连续两轮有新会话证据才降档。未报字段与显式零区分，超长输入或单会话主导时保持未知。未知渠道保留前三项与末级规则产生的位置。自由首轮流量的探索软预算为 5%，按会话复访延续；满额暂停接纳新探索会话。带已有上游资源引用时沿用原路由边界。

prefer 模式的会话亲和在亲和渠道合格时直接使用；渠道被禁用、健康暂停、满载或不在当前候选中时退回正常选路，不报错。strict 模式只用绑定渠道，熔断打开视为绑定渠道不可用，与上游对不可用亲和渠道的处理相同：返回 503 `strict_session_binding_unavailable`（带 Retry-After），除非开启 `keep_on_channel_disabled` 否则清除绑定，同一会话的下一个请求按正常选路并写回新绑定；半开且没有在途探测时本请求作为探测发送，探测占用时同样 503 并清除绑定；只因 429 冷却时照常发送并保留绑定；满载 429 和读取上限失败 503 都保留绑定。插件共享端点的正式重取与亲和选路共用同一条准入规则。固定、手动列表、原任务续作和已锁定的 WebSocket 不受影响。普通非 AdvancedCustom 渠道按 b388 原生规则不在选路阶段预筛 `/v1/responses/compact` 能力；高优先级不支持渠道可能在运行时返回不可重试 400，不能承诺转用次优渠道。AdvancedCustom 的路径校验、提供商插件身份和原生计数扩展的资格校验继续保留。非锁定重试分支在已收到供应商错误后遇到任何选路失败（无候选、全部满载、选路存储故障），HTTP、Responses WebSocket 和任务均保留上一次实际发送后返回的错误；任务通过传输层发送标记判断，包括响应解析产生的本地 502，原样保留 TaskError 的状态、数据及标志，实际选路错误仍记录日志。首轮没有供应商错误时返回当轮选路错误。任务显式取消优先返回 request_cancelled；原渠道锁定分支仍返回当次重新准入的倍率、权限、满载或存储错误。预扣和请求体失败不属于选路错误保留范围。任务在选路成功后、提交之前再次检查取消，已取消则不发送，返回 408 并由原生命周期退款及释放许可。

用户及渠道并发默认 0 表示无限，仍统计在途数，不排队。删除渠道或硬删除用户后，空闲的并发表项移除，仍有在途许可的表项在最后一个许可释放后移除。之后同 ID 的准入先读数据库：记录不存在就拒绝（选路跳过该渠道，prefer 亲和退回正常选路；用户请求返回 403 `user_unavailable`）。删除或改上限先提交数据库、再发布待刷新标记；标记生效后，删除前取得旧数据的请求不能重建表项，提交到发布之间已读到旧数据的请求仍按旧上限准入，这个窗口的上界未测量；同 ID 的记录重新存在时，新渠道或用户沿用在途计数并按数据库中的上限准入。用户槽覆盖逻辑请求及其重试；渠道槽覆盖一次真实尝试及资源清理。热更新保留活动计数，Release 幂等。用户满立即 429 `user_concurrency_exceeded`；渠道满扫描下一候选，全部合格渠道满时 429，无合格渠道则路由不可用。读取上限失败返回 503 `<kind>_concurrency_unavailable`，不再试下一个候选；strict 会话亲和遇到它同样返回 503 并保留绑定。普通 HTTP/WS 准入使用 `service.ConcurrencyAdmissionError` 映射。MJ image-seed 仍沿用上游封装：除满载外的准入错误返回 400 `code=4`，包括读取上限失败；不能将它声称为统一 503。

发送顺序为认证解析、用户占槽、选渠道、渠道占槽、资格与倍率复核、原生估算预扣、发送、观察与结算释放。每个逻辑调用只有一个 BillingSession；不使用信任免预扣，更贵重试须先有余额补足。模型基础价乘绑定渠道倍率一次，在原生最终取整前应用。任务在提交时保存渠道倍率和其他倍率（时长、尺寸等），后续改渠道倍率不影响在途任务。完成时按 token 重算的任务与上游一样读完成时的模型倍率配置：是否重算、模型倍率取多少都看那时的配置，管理员调价会影响在途任务的最终金额，调高多收、调低少收。见[资金实现](../billing/IMPLEMENTATION.md)。

Responses WS 按每次 create 重新认证、资格检查及占槽，空闲连接不占；不在连接内换渠道。Realtime 占整次连续会话。异步任务只在提交或实际轮询 HTTP 时占渠道槽，不在后台等待期间持槽。轮询时渠道满载或读取上限失败只跳过本轮，不计上游失败；准入时发现渠道已删除同样只跳过本轮；原生批量轮询读不到渠道时把任务判为失败且不退款，与上游相同，见[原生回归的行为变化](../upstream/NATIVE_B388_DISCLOSURES.md)。普通 HTTP 成功路径中，客户端断开不自动取消已发送的供应商请求；渠道槽位保持到供应商尝试结束，之后结算一次、释放一次。这个合同不承诺对失败响应禁止重试，也不承诺立即退款。

已接受任务的续作固定原渠道，不因 Key 偏好变化重放到其他渠道。插件原任务引用和 Midjourney 续作（change、simple-change、modal、video、action、image-seed）的原渠道准入由 `service.AcquireOriginTaskRouteChannel` 判定：只豁免手动列表，仍比较 Key 的最高渠道倍率。超限在渠道占槽、预扣、发送之前拒绝，不换渠道；没有上限或恰好等于上限允许。普通任务返回 400 `channel_ratio_exceeded`，MJ handler 保留自身封装；经 Distribute 提前拒绝的 MJ 提交仍使用 OpenAI 错误体。请求级路径、WS 和插件身份过滤器，渠道存在/启用、倍率合法及即时容量照常检查。找到 MJ 原任务后只准入一次、轮换一次 Key。

原渠道删除或禁用返回 400 `origin_task_channel_disabled`，满载 429，原渠道准入或 ApplyChannelPin 的存储故障 500；插件准备阶段仍沿上游统一返回 400 `origin_task_channel_disabled` 且不暴露底层错误；image-seed 的封装例外见上文。Key 模型限制保留上游现状。原生 remix 在原渠道上下文未初始化时仍可能发生 NewAPI 共有的 nil pointer panic，阻断后续预扣和发送。这个问题以及原模型推导、原生平台核对、remix 动作、ID 和继承倍率都与上游相同，没有在本地修复，见[等待上游](../upstream/WAITING_UPSTREAM.md)；不能声称这些路径已可用。插件原任务平台校验仍使用准备阶段候选元数据，尚不等同于实际执行插件的归属校验。

不存在或不属于当前用户的原任务、管理员指定渠道、存储失败与模型限制的错误顺序沿用共有实现；不承诺所有入口均在选路之前返回同一种不存在错误。MJ image-seed 仍使用吞掉数据库错误的旧查询，共有错误分类待上游处理。完整范围、源码位置与诊断见[等待上游列表](../upstream/WAITING_UPSTREAM.md)。

共享插件端点沿用上游的类别锁定：首次选中普通渠道后，重试不跨到插件渠道，反向亦然，手动列表顺延也受该规则约束。另有两项与上游相同的限制。先选路后解码，普通渠道胜出时不建立插件原任务 pin。选路不按 stream/sync/background 过滤插件候选，只支持 background 的插件渠道胜出时，stream/sync 请求返回 400。管理员可以把这类插件渠道的优先级调到可用普通渠道之下来规避；优先级相同时，健康、负载、延迟和权重排序仍可能选中插件渠道，普通渠道全部不可用时也会落到插件渠道。

主要接点为 `service/route_candidates.go`、`service/channel_select.go`、`service/concurrency.go`、`service/route_attempt.go`、`service/billing_session.go`。接口与版本冲突见[网关 API](GATEWAY_API.md)，不恢复 `/api/next` 或第二套路由管线。

预览的 `transport` 为 `http` 或 `websocket`，默认 `http`；`stream` 单独表示 HTTP 流式，WS 固定为流式且只支持 `/v1/responses`。预览与运行时共用路径资格、插件身份、宿主端点过滤器及模型规范化，使用同一插件注册表代际；响应回传实际解析的模型和传输方式。任务提交路径使用运行时的 VideoSubmit 观察桶排序。普通 HTTP 路径排除无关 TaskPlugin 渠道；共享宿主端点首次按原模型名允许合格的普通渠道及所有声明该端点的候选插件；原名无候选而回退到插件规范名后，追加与运行时一致的插件身份过滤，只保留该身份渠道。管理员给插件渠道声明非规范拼写时，阶段一命中后仍可能在执行时规范化并重新选路。`/v1/tasks/:key` 固定插件身份。其他依赖插件请求解码的路径返回 `400 preview_path_unsupported`。预览不运行 JS、不占槽、不预扣、不发送请求；共享端点依赖请求体的模式检查仍发生在执行时，静态资格不是提交成功保证。

多行渠道写和路由保存共用 `model.lockChannels`：完整 ID 集合去重、升序后再按 200 行分块；保存使用 SHARE，六个可达批量写入口使用 UPDATE。按 tag/status 取候选后锁定并按原数据库谓词复核，只修改实际锁住的行；渠道和能力行在同一事务内写入，通过事务读取更新值，提交后按实际 ID 发布缓存/并发/观察状态。多 Key 禁用预处理留在事务外。锁序为 Token（ID 升序）→渠道（ID 升序）→路由配置/条目，渠道→能力；历史无调用的 DeleteChannelByStatus/DeleteDisabledChannel 未扩改，不属于六入口覆盖。
